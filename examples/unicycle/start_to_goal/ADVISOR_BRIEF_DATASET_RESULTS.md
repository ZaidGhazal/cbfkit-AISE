# Operational-Rule Dataset Generation: Advisor Brief

## 1. Objective
This work generates safety-labeled operational datasets for unicycle navigation in obstacle-rich scenarios, then compares controller behavior under identical test conditions.

The primary objective is to evaluate how Control Barrier Function (CBF)-based controllers improve safety relative to a nominal legacy controller, especially on cases that are likely to induce safety violations.

---

## 2. Problem Background and Motivation
In start-to-goal navigation, a controller can track a goal well while still violating safety constraints near obstacles. This is a core tension:

- Goal reaching and trajectory tracking encourage progress.
- Safety constraints require maintaining a non-violation set at all times.

In this dataset pipeline, safety is represented through a barrier-like safety signal:

- `h_safe(x,t) = ||p - p_obs(t)||^2 - r^2`
- `h_safe >= 0`: safe (outside obstacle boundary)
- `h_safe < 0`: unsafe (inside obstacle boundary)

The data generation framework intentionally includes both safe and unsafe outcomes (with configurable sampling) so downstream analysis/training can learn meaningful separation and controller tradeoffs.

---

## 3. Systems Covered
The current script targets two unicycle systems:

1. `unicycle_static_obstacle`
- Obstacle is fixed at the world origin.

2. `unicycle_dynamic_obstacle`
- Obstacle translates with sampled speed and heading.

Both systems are generated by:
- `examples/unicycle/start_to_goal/generate_operational_rule_datasets.py`

---

## 4. Safety and Logical-Case Enforcement
To avoid non-physical or meaningless initial conditions, the generator enforces logical starts:

- Robot must not start inside obstacle.
- Robot must not start on obstacle boundary.
- Robot must satisfy a minimum clearance margin at `t=0`.

Current rule:
- `initial_distance_to_obstacle - obstacle_radius > 0.05 m`

This rule is enforced in both:
- Sampling stage (candidate rejection)
- Simulation stage (fail-fast validation)

## 5. Controllers Used in the Study

### 5.1 Legacy Controller (Baseline)
Legacy uses a nominal proportional unicycle controller with no CBF safety constraints in the optimization:

- Position gain: `Kp_pos`
- Heading gain: `Kp_theta`
- Desired state: `[4.0, 0.0, 0.0, 0.0]`

This controller prioritizes task tracking, and can violate safety depending on initial condition and obstacle motion.

### 5.2 Evolved Controller (CBF-based)
The evolved controller is a QP-based CBF controller that modifies control actions to satisfy barrier constraints.

Two modes now supported in the generator:

1. `vanilla` CBF-QP
- API: `vanilla_cbf_clf_qp_controller`
- Uses standard zeroing-CBF constraint structure.

2. `robust` CBF-QP
- API: `robust_cbf_clf_qp_controller`
- Adds robustness margin against bounded disturbances.
- Requires disturbance settings:
  - `disturbance_norm_bound`
  - `disturbance_norm` in `{2, inf}`

Controller selection is configurable via CLI:
- `--cbf-controller {vanilla,robust}`

## 6. How `h(x)` Drives Evolved Control Adaptation
The generator logs and evaluates a safety signal over time. Two related functions are used:

1. Labeling safety function:
- `h_safe(x,t) = ||p - p_obs(t)||^2 - r^2`
- Used to compute `min_h` and Pass/Fail labels.

2. Controller barrier function (velocity-aware):
- Includes additional heading/velocity shaping term in the CBF certificate:
- Encourages anticipatory behavior when moving toward obstacle.

### 6.1 Symbol definitions for `h`
For clarity, the key terms are:

- `x`: full robot state (for this unicycle: position, speed, heading)
- `p = [x_pos, y_pos]`: robot 2D position extracted from state
- `p_obs(t) = [x_obs(t), y_obs(t)]`: obstacle center position at time `t`
- `r`: obstacle radius
- `||p - p_obs(t)||`: Euclidean distance from robot center to obstacle center
- `v`: robot forward speed
- `theta`: robot heading angle
- `k_v`: velocity weight used in the velocity-aware controller barrier term

Labeling safety function:
- `h_safe(x,t) = ||p - p_obs(t)||^2 - r^2`

Interpretation:
- `h_safe > 0`: outside obstacle (safe)
- `h_safe = 0`: exactly on boundary
- `h_safe < 0`: inside obstacle (unsafe)

Velocity-aware controller barrier term (used inside evolved controller constraints):
- `h_cbf(x,t) = ||p - p_obs(t)||^2 - r^2 + k_v * v * <p - p_obs(t), [cos(theta), sin(theta)]>`
- `<a,b>` denotes dot product.
- This extra term biases control behavior based on motion direction and speed, helping anticipatory avoidance.

### 6.2 Worked numeric example
Assume at one timestep:

- Robot position: `p = [1.2, 0.3]`
- Obstacle center: `p_obs = [0.0, 0.0]`
- Obstacle radius: `r = 1.0`

Compute:
- `||p - p_obs||^2 = 1.2^2 + 0.3^2 = 1.53`
- `h_safe = 1.53 - 1.0^2 = 0.53`  -> safe (`h_safe > 0`)

If robot moves closer, e.g. `p = [0.6, 0.2]`:
- `||p - p_obs||^2 = 0.36 + 0.04 = 0.40`
- `h_safe = 0.40 - 1.0 = -0.60`  -> unsafe (`h_safe < 0`)

This is exactly why `min_h` over the trajectory is used for Pass/Fail labeling.

### Mechanism in practice
- When the robot is far from obstacle (`h` large), evolved control stays close to nominal.
- As robot approaches safety boundary (`h -> 0`), QP constraints become active.
- Control is altered (turn/brake/redirect) to keep the trajectory in the safe set.
- If QP becomes infeasible, the script currently keeps simulation running by fallback handling and logs controller error flags.

## 7. Dataset Contents
Per system directory:

- `D_legacy.csv`
  - One row per case, legacy outcome.
- `D_evolved.csv`
  - Evolved outcomes (currently filtered to Pass rows in this pipeline).
- `D_paired_comparison.csv` (optional)
  - Side-by-side legacy/evolved outcomes for same `case_id`.
- `D_legacy_step_logs.csv`
  - Per-timestep state, safety value `h`, controller stats, runtime.
- `D_evolved_step_logs.csv`
  - Same format for evolved runs.
- `metadata.json`
  - Features, bounds, seeds, controller params, generation settings.

Root output:
- `summary.json`

---

## 7.1 `D_paired_comparison.csv` Column Guide
`D_paired_comparison.csv` contains one row per test case, with legacy and evolved outcomes side-by-side for the same sampled initial condition.

### Identity and input columns
- `case_id`
  - Integer case index used to align rows across all exported files.
- Feature columns (system-dependent, copied from sampled input vector):
  - Static system:
    - `initial_distance_to_obstacle`
    - `initial_speed`
    - `obstacle_radius`
    - `initial_heading_error`
  - Dynamic system adds:
    - `obstacle_speed`
    - `obstacle_heading`

### Legacy controller result columns
- `legacy_label`
  - `Pass` if `min_h >= 0`, else `Fail`.
- `legacy_min_h`
  - Minimum value of `h_safe` along the simulated trajectory for legacy control.
  - More negative means deeper safety violation.
- `legacy_controller_error`
  - Boolean flag for controller/QP-related error states recorded during simulation.
- `legacy_case_runtime_s`
  - Wall-clock simulation runtime (seconds) for that case using legacy controller.

### Evolved controller result columns
- `evolved_label`
  - `Pass` if `min_h >= 0`, else `Fail`.
- `evolved_min_h`
  - Minimum value of `h_safe` over trajectory for evolved controller.
- `evolved_controller_error`
  - Boolean flag for controller/QP-related error states recorded during evolved run.
- `evolved_case_runtime_s`
  - Wall-clock simulation runtime (seconds) for that case using evolved controller.

### How to read one row
- Same `case_id` and same input features feed both controllers.
- Compare `legacy_min_h` vs `evolved_min_h`:
  - If evolved is higher (less negative or more positive), safety margin improved.
- Compare `legacy_label` vs `evolved_label`:
  - `Fail -> Pass` indicates safety recovery by evolved controller.
- Compare `*_case_runtime_s`:
  - Shows computational overhead/tradeoff for evolved safety control.

---

## 7.2 `D_legacy_step_logs.csv` and `D_evolved_step_logs.csv` Column Guide
These files are per-timestep logs (long format): each row is one simulation time step for one `case_id`.

### Core trajectory/safety columns
- `case_id`
  - Links timestep rows back to case-level CSV files.
- `label`
  - Final case label (`Pass`/`Fail`) for that controller run.
- `controller_error`
  - Final case-level error flag for that run.
- `case_runtime_s`
  - Total wall-clock runtime for the full case simulation.
- `step`
  - Timestep index (starts at 1 after initial condition).
- `time_s`
  - Physical simulation time in seconds.
- `state_x`
  - Robot x-position at this timestep.
- `state_y`
  - Robot y-position at this timestep.
- `state_v`
  - Robot forward speed at this timestep.
- `state_theta`
  - Robot heading angle at this timestep.
- `h`
  - Safety value `h_safe(x,t)` at this timestep.

### Controller diagnostics column
- `controller_stats_json`
  - JSON-encoded per-step diagnostic dictionary exported from controller `dkeys/dvalues`.
  - May include fields such as `error`, `qp_error`, `complete`, and solver-related entries.
  - Stored as one column to keep step-log schema stable and support streaming writes during long runs.

### How to read these files
- Use `D_legacy_step_logs.csv` to inspect when/where legacy first violates safety (`h < 0`).
- Use `D_evolved_step_logs.csv` to verify if evolved control keeps `h` nonnegative or delays violation.
- Join on `case_id` with `D_paired_comparison.csv` for side-by-side case interpretation.

## 8. Generation Modes and Balancing

### 8.1 Standard mode
Uniform random sampling over feature bounds (with logical-case rejection).

### 8.2 Failure-focused mode
Sampling accepts cases preferentially according to failure criterion:
- `--failure-target {legacy,evolved,either,both}`

### 8.3 Mixed variation mode
To avoid over-concentrating on failure-only data:
- `--random-sample-percentage`

This reserves a user-defined fraction of accepted cases as random logical cases (not forced to fail), increasing dataset variation and reducing mode collapse.

---

## 9. Runtime Reliability Features
To reduce risk of data loss in long runs:

- Progressive checkpoint CSV writes during execution (`--checkpoint-every`)
- Progress logs in terminal (`--print-every`)
- Timing logs every 5 cases
- Per-system elapsed-time report
- Total script elapsed-time report

This allows partial data recovery if runs stop unexpectedly.

---

## 10. Interpreting Results (Vanilla vs Robust, 100 Samples Each)
For your two 100-sample runs (vanilla and robust), key comparison dimensions:

1. Safety outcomes
- `Pass/Fail` counts in legacy vs evolved.
- `min_h` distributions.

2. Control reliability
- `controller_error` frequency.
- Any QP infeasibility patterns by scenario type.

3. Runtime/complexity
- `case_runtime_s` mean/variance.
- Throughput under comparable settings.

4. Behavior quality
- Inspect trajectory and first-failure points using:
  - `examples/unicycle/start_to_goal/visualize_operational_rule_simulations.py`

Recommended advisor-facing message:
- Vanilla CBF improves safety under nominal assumptions.
- Robust CBF trades additional conservatism/computation for disturbance tolerance.
- Mixed failure/random sampling gives broader operational coverage for downstream modeling.

## 13. Reproducibility and Traceability
Each run stores:

- Random seeds (sampling and controller runs)
- Batch seed context (`batch_index`, `batch_seed_stride`, and effective `seed_offset`) when used for multi-batch generation
- Controller parameters and selected CBF variant
- Simulation horizon and step size
- Dataset-size and label-count summaries

This supports reruns, auditing, and apples-to-apples comparison across controller settings.
